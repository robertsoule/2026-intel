\section*{Intel Connectivity: A Hardware Accelerator for Key-Value (KV) Caches}

\PAR{Principal Investigators:} Robert Soul{\'e} and Rajit Manohar
(\{robert.soule, rajit.manohar\}@yale.edu), Departments of Computer Science and Computer Engineering,
Yale University 10 Hillhouse Avenue,, New Haven, CT, 06511.

\PAR{Intel contact and sponsor:} James Tsai
  (\href{james.tsai@intel.com}{james.tsai@intel.com})



\PAR{Problem Statement.}
%
Large Language Models (LLMs) are only effective if their context is
large.  The context allows the LLM to understand continuing
conversations, follow multi-step directions, and process large
documents and codebases. An LLM's active runtime context is stored in
the key-value cache (KV cache).  As the model generates new tokens one
by one, it appends them to the cache and accesses the stored keys and
values to understand the ongoing context. However, for each token
generated in an inference pipeline, the number of floating-point
operations (FLOPs) per byte of memory read is very low. At the same
time, hardware compute power has grown much faster than memory
transfer speed. As a consequence, the limiting factor for performance
for inference pipelines is memory bandwidth.

Today, the state-of-the-art pipeline design deploys the KV cache on a
GPU, where High-Bandwidth Memory (HBM) allows for high-throughput
memory requests. However, as model and context sizes grow, the context
often exceeds the capacity of GPU HBM, necessitating moving gigabytes
of key and value vectors back and forth across the PCIe slot from CPU
RAM to the GPU.

Different models have developed various software strategies for
optimizing the KV Cache. The original transformer
architecture~\cite{vaswani2017} used Multi-Head Attention (MHA), which
splits data into several "heads", with each head computing scaled
dot-product attention independently (i.e., there are $N$ query heads,
$N$ key heads, $N$ value heads).  Models such as Google's PaLM and
Technology Innovation Institute's Falcon 7B, adopted Multi-Query
Attention (MQA)~\cite{shazeer2019}, which collapses the key and value
heads down to just one shared head for the entire layer.  (i.e., $N$
query heads, 1 key head, 1 value head).  Llama 2 and Gemma used
Grouped-Query Attention (GQA)~\cite{ainslie2023}, which splits query
heads into groups (e.g., N/8 key/value heads).  DeepSeek-V2 introduced
Multi-head Latent Attention (MLA)~\cite{deepseekv2}, which compresses
high-dimensional key-value (KV) states into a tiny, low-dimensional
latent vectors.

Likely, the last word has not yet been written on KV Cache compression
or management technique. But, what is clear is that any solution will
need to effectively leverage both on-chip and off-chip memory access.
While decades of research has taught us that this is a hard problem in
general, inference workload memory access patterns are extremely
predictable, suggesting that it should be possible to develop
effective high-bandwidth KV cache management algorithms analagous to
cache hierarchies in modern CPUs. However, unlike CPUs, which have
hard coded pre-fetch and cache replacement policies, KV Caches need
flexibility to adapt to model and workload changes.

Rather that proposing a pure software solution, this project proposes
the development of dedicated programmable hardware to enable
low-latency, high-bandwidth KV Cache access and management.

\PAR{Project Goals.}
%
The central goal of this proposal is to: \emph{develop a programmable
hardware accelerator for the KV cache}. The accelerator is
CPU-attached, so that it can leverage CPU software/hardware resources
to access the largest memory capacity possible. A KV cache request
will be associated with a specific context tag and layer identifer,
where the layer identifier can be used to determine the location of
the (K,V) entries in the memory hierarchy.



\begin{alltt}\scriptsize
  - You don't have enough memory to accomodate all data
  - you need to coordinate the ``master set''
  - need to hide latency in accessing the master set
- We have a scratch pad (i.e., accelerated managed memory, on chip SRAM)
- Dot product
- model meta data, which tells you how to do the pre-fetching, what is
currently active
- a programmable/extensible prefetch mechanism (orchestrate for JIT
  prefetch)
  - Runtime support to inform the prefetch mechanism of requests/workload
  - low latency memory-to-network  data transfer (possibly RDMA, but
    maybe not)
\end{alltt}

\PAR{Anticipated Impact or Tech Transfer to Intel.}
%
There is considerable competition to develop low-latency
inference pipelines. Companies like Cerebras, Grok, Groq, and
Etched are all proposing alternatives to NVidia's GPU
hegemony. However, all of these efforts focus on compute
performance, rather than the KV Cache performance. If this
project is successful, it will have a significant and broad
impact, as all of these options face the memory bottleneck.

The results of this work will be disseminated in top-tier technical
conferences (e.g., SOSP, OSDI, ASPLOS, etc.) and the artifacts will be
placed in the public domain under an open-source license.
These results and artifacts can be used to inform possible
enhancements to IPU and CPU architectures to enable
the deployment of high-performance KV Caches.

The student funded by this project will be encouraged to intern
at Intel during the summer, allowing for a direct transfer of
knowledge. Moreover, the PIs have a long history of close
collaboration with Intel. Indeed, both PIs have worked as
contractors for Intel in the past.


\PAR{Evaluation Plan.}
%
Our primary metric of interest is \emph{Time Per Output Token} (TPOT), i.e., the average time required to generate each token after the first one. We will evaluate our proposed design using a variety of workloads (e.g., prompts) and context sizes. As baseline comparisons, we will quantify the performance of our KV Cache accelerator against a variety of software strategies for KV Cache management, including Multi-Head Attention~\cite{vaswani2017}, and Multi-Query Attention~\cite{shazeer2019}, Grouped Query Attention~\cite{ainslie2023}, and Multi-head Latent Attention~\cite{deepseekv2}.

\PAR{Project Deliverables.}
%
The work described in this proposal will be conducted by a
team of two PIs and one graduate student. The project will
feature three major demonstrator milestones at yearly intervals.
\begin{itemize}[leftmargin=*]
\item \emph{Year 1:} An architectural study and workload analysis of a diverse set of models and
  their KV Cache access patterns. The study will also inform detailed design document for the
  proposed KV Cache accelerator.
\item \emph{Year 2:} An initial proof-of-concept artifact in the form of an FPGA prototype. The
  RTL will be released under an as open source license.
\item \emph{Year 3:} An improved FPGA prototype that improves on the initial release by:
  (i) optimizing communication overhead for remote memory
  access and (ii) updates the design to incorporate anticipated changes in LLM algorithms.
\end{itemize}
    

\PAR{Biggest Technical Risk.}
%
The proposed project is ambitious, and as with any research proposal,
carries with it a certain amount of uncertainty.
To some extent, we have de-risked the project, as the PIs
have developed several FPGA-based prototype systems in the past.
That said, the largest possible threat to the success of this
project, in our opinion, would be if we discovered that
KV Caches require significant changes to the current CPU off-chip 
interfaces. However, we think this risk is partially mitigated
by the fact that industry-standard I/O and memory interfaces have
been standardized and, in many cases, driven by Intel (e.g., PCIe).


\PAR{Impact to Intel If Not Pursued.}
%
KV Cache latency is a critical problem for inference
pipelines that is actively
being investigated both by academia and industry.
If Intel does not offer a solution, industry would
adopt alternative approaches.

\PAR{Differentiation from Existing Projects.}
%
As discussed above, there have been significant efforts
in designing algorithms to improve KV Cache usage and
management. Rather than a pure software-based approach,
we are proposing an extensible hardware-software co-design that
optimizes the KV Cache access.


\PAR{Research Team.}
%
The proposed work will be carried out by a team of three researchers:
