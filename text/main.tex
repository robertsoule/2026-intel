(\{robert.soule, rajit.manohar\}@yale.edu), Departments of Computer Science and Computer Engineering,
Yale University 10 Hillhouse Avenue,, New Haven, CT, 06511.

\PAR{Intel contact and sponsor:} James Tsai

\PAR{Problem Statement.}
%
Large Language Models (LLMs) are only effective if their context is
large.  The context allows the LLM to understand continuing
conversations, follow multi-step directions, and process large
documents and codebases. An LLM's active runtime context is stored in
the key-value cache (KV cache).  As the model generates new tokens one
by one, it appends them to the cache and accesses the stored keys and
values to understand the ongoing context. However, for each token
generated in an inference pipeline, the number of floating-point
operations (FLOPs) per byte of memory read is very low. At the same
time, hardware compute power has grown much faster than memory
transfer speed. As a consequence, the limiting factor for performance
for inference pipelines is memory bandwidth.

Today, the state-of-the-art pipeline design deploys the KV cache on a
GPU, where High-Bandwidth Memory (HBM) allows for high-throughput
memory requests. However, as model and context sizes grow, the context
often exceeds the capacity of GPU HBM, necessitating moving gigabytes
of key and value vectors back and forth across the PCIe slot from CPU
RAM to the GPU.



\begin{alltt}\scriptsize
  - LLMs are only effective if the context is large
  - As a consequence, the limiting factor for performance is memory bandwidth
  - Today, state of the art is you run KV cache using GPU HBM
  - Different models have different strategies for optimizing the KV Cache
  - But, given a model, the access is very predictable
  - This calls for a programmable memory hierarchy that leverages
  hybrid on-chip and off-chip memory access
  - So, we get an effective high-bandwidth KV cache in a similar way
  to the cache hierarchy in a modern CPU
  - Unlike the CPU, though, where you have a baked in pre-fetch and caching
  policy, we need more flexibility because the model changes the way
  the KV cache is used (See DeepSeek approach, etc.)
\end{alltt}
  


Attention~\cite{vaswani2017}


\PAR{Project Goals.}
%
The central goal of this proposal is to: \emph{develop a
programmable accelerator for the KV cache}

\begin{alltt}\scriptsize
We will evaluate one accelerator on three different strategies:
- Multi-Head Attention (MHA)~\cite{vaswani2017} and Multi-Query Attention~\cite{shazeer2019}


- shared (grouped) attention GQA~\cite{ainslie2023}
- Multi-head Latent Attention (MLA)~\cite{deepseekv2}  (i.e., low rank factorization)
\end{alltt}
  
\begin{alltt}\scriptsize
  - You don't have enough memory to accomodate all data
  - you need to coordinate the ``master set''
  - need to hide latency in accessing the master set
- We have a scratch pad (i.e., accelerated managed memory, on chip SRAM)
- Dot product
- model meta data, which tells you how to do the pre-fetching, what is
currently active
- a programmable/extensible prefetch mechanism (orchestrate for JIT
  prefetch)
  - Runtime support to inform the prefetch mechanism of requests/workload
  - low latency memory-to-network  data transfer (possibly RDMA, but
    maybe not)
\end{alltt}
